* Why move off nixos-raspberrypi

nixos-raspberrypi builds the vendor kernel against /its own/ nixpkgs pin
(25.11) so it can serve prebuilt binaries from cachix. Running it under this
flake's nixos-unstable is exactly what has hurt:

- the =passthru.target= graft hack in =configuration.nix= (their kernel predates
  a nixpkgs bootloader-module change),
- ZFS opted out because the cachix cache lacks the kernel's =-dev= output,
- eval-breakage risk on every nixpkgs bump, since their modules and ours
  disagree about nixpkgs versions,
- their cachix substituter wired into both prometheus /and/ hyperion.

Meanwhile [2026-08-07 Fri]:

- nixpkgs never had a Pi 5 vendor kernel and deprecated the whole
  =linux_rpi*= family (2026-04, PR 477665) with an eval warning that says to
  use nixos-hardware instead.
- nixos-hardware grew a =raspberry-pi/5= profile (2026-01, commit =c8f766f=),
  actively maintained. It builds the vendor kernel /against this flake's
  nixpkgs/, and everything else in its boot path is a stock nixpkgs package
  (=raspberrypifw=, =ubootRaspberryPiAarch64=, =generic-extlinux-compatible=).
- The one cost, verified by dry-run: nobody caches that kernel. The
  =linux-rpi-6.18.34-stable_20260609= derivation lands in "will be built" —
  we compile it on our own infra, and harmonia serves it afterwards.

** Why not mainline (yet)

Mainline 6.18 covers the headless feature set (SD since v6.12, PCIe/NVMe
v6.16, RP1 south bridge v6.17, RP1 gigabit ethernet + USB3 v6.18), but two
things disqualify it for this host today:

1. No thermal/fan support at all: mainline's =bcm2712= DT has no
   thermal-zones, no cooling maps, and no RP1 PWM driver exists upstream. A
   CI runner under sustained compile load would sit at the firmware throttle
   ceiling with an inert active cooler.
2. The DTB schema trap: the NixOS boot chain hands the kernel the
   /downstream/-schema DTB (from =raspberrypifw=, via the GPU firmware and
   U-Boot). Mainline's RP1 driver expects a structurally different topology.
   Kernel 6.18 tolerates the mismatch via a PCI quirk; v6.19 deliberately
   removed that fallback — a routine kernel bump could silently cost the
   ethernet on a headless box.

Revisit when mainline gains RP1 PWM + bcm2712 thermal-zones AND the DTB
story is settled (either the boot chain loads mainline DTBs by default or
the RP1 driver regains firmware-DTB tolerance).

* Target state

| aspect         | before (nixos-raspberrypi)                      | after (nixos-hardware)                                  |
|----------------+-------------------------------------------------+---------------------------------------------------------|
| kernel         | vendor 6.18.42, tag =unstable_20260806=, foreign pin | vendor 6.18.34, tag =stable_20260609=, our nixpkgs |
| kernel binaries | nixos-raspberrypi.cachix.org                   | built natively on prometheus, served by its harmonia    |
| boot chain     | GPU firmware → kernel directly ("kernel" bootloader) | GPU firmware → =u-boot.bin= → =extlinux.conf=      |
| generations    | on the FAT firmware partition                   | on the ext4 root (=/boot/extlinux=), FAT holds firmware only |
| firmware files | nixos-raspberrypi module                        | =hardware.raspberry-pi.firmware= activation script      |
| config.txt     | nixos-raspberrypi generated                     | =hardware.raspberry-pi.configtxt= (=kernel=u-boot.bin=; pi5 =enable_uart=0= default) |
| page size      | 16K                                             | 16K (=bcm2712_defconfig= sets =ARM64_16K_PAGES=y= — verified at the pinned tag) |
| filesystems    | =FIRMWARE= vfat + =NIXOS_SD= ext4               | unchanged; =sd-image-aarch64.nix= declares the same labels |
| sd image       | nixos-raspberrypi sd-image module               | nixpkgs =sd-image-aarch64.nix=                          |

Invariants worth stating: same SD card, no repartitioning; DTBs stay
vendor-schema (coherent with the vendor kernel); U-Boot keeps using the
firmware-provided DTB (=uboot.enable= sets
=generic-extlinux-compatible.useGenerationDeviceTree = false=, so
=extlinux.conf= carries no =FDTDIR= line and config.txt overlays survive).

Two gotchas the module reads surfaced:

- The =raspberry-pi-5= profile does /not/ enable the firmware install or
  U-Boot chainload by default — =hardware.raspberry-pi.firmware.enable= and
  =.uboot.enable= must both be set explicitly, or the SD image and the
  running system get an =extlinux.conf= nothing ever reads.
- hyperion's nixos-raspberrypi cachix entries are what let it deploy
  prometheus today (binfmt emulation + substitution). They must be
  /replaced/ by prometheus's harmonia, not merely deleted, or future
  =deploy-rs= runs will rebuild the kernel under QEMU (Phase 4).

** TODO Phase 2: pre-build natively on prometheus [/]

hyperion deploys aarch64 via binfmt emulation plus substituters. Without
this phase, the first deploy or CI run would compile the kernel under QEMU
(hyperion) or eat hours of the Pi runner mid-merge. Building natively from
the branch primes prometheus's store — and its harmonia — ahead of time,
and proves the config builds before main is touched.

- [ ] On prometheus, inside a zellij session (the build runs for hours):
  #+begin_src nushell

  cd dotfiles
  git switch <migration-branch>
  nix build -L '.#nixosConfigurations.prometheus.config.system.build.toplevel'
  #+end_src

* Failure modes and rollback

** Switched but not yet rebooted, want out
The old generation is still installed. =sudo nixos-rebuild switch
--rollback= re-runs the nixos-raspberrypi activation, which rewrites
config.txt back to direct-kernel boot and re-copies its DTBs. Verify
=config.txt= afterwards before any reboot — this is a boot-chain swap in
reverse and deserves the same pre-reboot checklist.

** Reboot fails (host never comes back)
Pull the SD card and mount the FAT partition on another machine:
- Restore =config.txt= from the Phase 0 snapshot. The old kernel files are
  still on the partition — the new firmware install only prunes =*.dtb=
  and =overlays/*=, and Phase 5's cleanup hasn't run yet.
- The old vendor DTBs /were/ pruned, but the =raspberrypifw= vendor DTBs
  now present are downstream-schema and boot the old vendor kernel fine.

** SD card dead / total loss
Flash the Phase 2 recovery image. Then restore identity: unpack
=prometheus_etc_ssh.tgz= over =/etc/ssh= (restores the sops age identity
and SSH host identity), restore =/var/lib/netbird= or re-enroll with a
fresh setup key, reboot.

* Operational costs going forward

- Kernel rebuilds recur on every nixos-hardware kernel-tag bump /and/ every
  nixpkgs stdenv mass-rebuild — each one is a multi-hour native build on
  the prometheus runner. CI absorbs it (timeout raised in Phase 1);
  deploys stay fast because harmonia serves the result.
- EEPROM updates are manual now (=rpi-eeprom-update= from the
  =raspberrypi-eeprom= package); nixos-raspberrypi had its own wiring.
- nixos-hardware couples its kernel tag to =raspberryPiWirelessFirmware=
  freshness — irrelevant to this wired-only host, but worth remembering if
  WiFi is ever enabled.
